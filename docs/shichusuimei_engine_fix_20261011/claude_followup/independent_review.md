## 2. 詳細

### 2.1 P1-A(`shichusuimei_annual_report.py:141-160`)

**正しいと確認した点**

- 版の比較は数値タプルで行われています。`"0.10.0"` を正しく扱い、空文字・`"v0.4"`・`"0.5.0rc1"` は ValueError で legacy=True になります。安全側の判定です。
- 前回の導出(旧 idx = ⌊JDN+50−f/24⌋、f≤0 で +1)と、`offset <= 0` の条件は一致しています。
- 新しい原本(0.5.0)は False に固定され、原本の dict は変更されません(deepcopy と snapshot 比較のテストあり)。

**残る条件**

1. `input.timezone_offset_hours` が「出生時点の夏時間込みの実オフセット」でない場合、旧エンジンが実際に使った f と食い違います。
   - 標準時のオフセットが保存されていると、London の夏生まれ(f=+1、保存 0)は偽陽性になります。これは無害です。
   - 逆の食い違い(保存値 >0、実際の f ≤0)は、時差が負の地域ではまず起きませんが、保存値の由来は未検証です。
2. フラグは `calculation` の中にしかありません。`interpretation_flags` には `natal_day_pillar_verified_by_this_report: False` しかなく、日柱が疑わしいという情報がありません。prompt_builder や購入者向け表示が `legacy_reference_notes` を拾うかどうかは未提示です。拾わない場合、AI が誤った日主で鑑定文を書きます。
3. テストは fixture が legacy であり、`time_context` を持たないことを前提にしています。版を明示していないので、fixture を 0.5.0 で再生成すると、このテストは意図と違う理由で落ちます。`engine_version` をテスト内で明示的に設定することを推奨します。

### 2.2 P1-B(変更履歴の不足 → FAIL)

`api_version` の切替は PASS です。条件は、西洋単独で `systems.shichusuimei` が `None` または未設定であることです。`{}` だと 1.1 になります。西洋・トランジットが 1.0 のままであることを確かめる回帰テストはありません。

変更履歴が挙げているのは日替わりの変更だけです。次の項目も同じ 1.1 で結果が変わりますが、記載がありません。

| 変更 | 最小反例 |
|---|---|
| UTC オフセット ≤0 の日柱(全時刻) | `timezone=America/Los_Angeles`、2000-01-07 12:00 → 旧 乙丑、新 甲子 |
| gender 省略時の大運 | API の既定 `gender="unknown"`(`api_calc.py:321`)→ 旧は女性で補完した大運、新は空(undetermined)。**省略していた全利用者が対象**です |
| 海外の出生地で timezone を省略 | 旧は Asia/Tokyo で 200、新は 400 `INVALID_TIMEZONE` |
| 新しいエラーコード | `INVALID_DAY_BOUNDARY`、`INVALID_BIRTH_DATETIME`(夏時間の重複・欠落時刻) |

エラー応答には `meta` がありません。そのため、利用者はエラー時に版を判別できません。これは P3 です。

### 2.3 P1-D / P2-F の偽陽性条件

- **女性補完の誤判定**: `legacy_imputed` は `_parse_gender(input.gender)=="unknown"` で判定しています。旧形式で `input.gender` が**欠けている** YAML では、購入者が実際に女性を選んでいても補完扱いになり、注記の文面が事実と異なります。addon でも `unknown` になって大運が空になります。旧 Full YAML が常に `input.gender` を持っていたかどうかの確認が必要です。
- **`_parse_gender` が例外を投げる場合**: 想定外の文字列(例: `"女性"`)で ValueError を投げる実装だと、これまで生成できていた旧原本の年報告が新たに失敗します(未検証)。

## 3. 新規の反例

**N1(P2): `timezone` が偽値の非文字列だと、海外の出生地でも東京に黙って補完される**

- 箇所: `api_calc.py:151-158` と `:138`
- 入力: `{"birth_place":"Los Angeles","timezone":false}`(`0` や `[]` も同じ)
- 経過: `raw=False` は None ではありません。`str(False)="False"` は空でないので検査を通ります。`_normalize_timezone` は `payload.get("timezone") or payload.get("tz_name") or "Asia/Tokyo"` で値を読み直し、Asia/Tokyo を返します。
- 結果: 200 が返り、Asia/Tokyo で計算されます。「海外は UTC や東京に補完しない」という保護をすり抜けます。
- 修正: `raw` が `str` であることを要求し、`raw` 自体を `ZoneInfo` で検証して返します。payload を再読しないようにします。

**N2(P2・条件付): addon_type が `western_long_term_transits_addon` だと四柱の経路に落ちる**

- 箇所: `routes.py` の `_validate_addon_base_doc` / `_build_addon_yaml_from_base`
- validate はこの型を通しますが、build には分岐がないため、末尾の四柱 addon の生成に進みます。
- 結果:
  - 四柱を含む原本では、四柱の大運 YAML が返り、注文は long_term として消費されます。
  - 四柱を含まない原本では、「日柱を照合できない」という見当違いのエラーになります。
- 直前の `RedirectResponse(...token...)` がこの型を先に処理しているなら到達しませんが、その部分は提示されていません。
- 修正: 四柱の経路の冒頭で `if addon_type != "shichu_fortune_cycles_addon": raise` を入れます。

**N3(P2・条件付): 旧 addon のテストは生成関数をモックしている**

- `fake(**args)` はどんなキーワード引数も受け取ります。そのため、本物の `build_shichu_fortune_cycles_addon_yaml` が `birth_utc_offset_hours`・`birth_fold`・`day_boundary_hour` を受け取れなくても、テストは通ります。
- モックを使わない統合テストを1件追加することを推奨します。fixture は旧形式で、Tokyo、オフセット 9 のものを使います。

**N4(P3): オフセット一致の許容誤差 `1e-9`**

- 箇所: `birth_datetime.py:46`
- LMT 時代(Tokyo は 1888 年前で +9:18:59 = 9.31638…)の出生では、保存時にオフセットを丸めていると、全候補が除外されて拒否されます。安全側に倒れますが、年報告が対応する 1800 年以降の範囲で addon が使えない場合があります。
- 秒単位で比較するか、保存精度に合わせた許容誤差にします。

**N5(P3): `day_change_at_23` の型ガードが `day_boundary_hour` 指定時にも働く**

- `day_change_at_23=None, day_boundary_hour=23` も拒否されます。
- 報告どおり、直接の呼出元が yaml_exporter だけであれば、その既定値が `False` であることが条件です(`None` だと全件が例外になります)。

**N6(P3): API の `day_boundary` で JSON の型により意味が分かれる**

- JSON の `false` は 01:00、JSON の `0` は 00:00 です。enum として定義どおりですが、変更履歴に1行あると誤用を防げます。

## 4. 確認できた保護(反例なし)

- **注文の消費順序**: 提示された addon の経路では、`_build_addon_yaml_from_base` が例外を投げると `_redeem_addon_order_or_raise` に到達しません。日柱の不一致や照合不能で拒否した場合、注文は消費されません。基本フォーム側の順序は提示されていないので、報告に依拠しています。
- **旧 addon の日替わり対応**: 旧 OFF→0、旧 ON/子刻後半→1、新しい原本は保存値を使います。`day_change_at_23` には常に bool が渡ります。
- **日本 1949 の夏時間**: 1949-01-01 が土曜日なので、9月1日は木曜日です。最初の「土曜日 ≥8」は 9/10 で、25:00 は 9/11 01:00 夏時間です。00:00〜00:59 が重複するので、00:30 は曖昧になります。fold0 で +10、fold1 で +9、UTC 差は 1 時間で、テストの期待値と一致します。tzdata の規則は記憶に基づいており、実行はしていません。
- **timezone の null と alias**: null のときに `tz_name` を使う挙動は意図どおりです。明示的な空文字は 400 で、旧来と同じです。
