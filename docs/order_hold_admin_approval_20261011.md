## 変更した動作

| 状態 | 通常同期 | 発行・承認 |
|---|---|---|
| 初回の正常な購入通知 | 従来の明細単位の発行権を作成 | 従来の購入者入力で発行可能 |
| 未分類通知 | 保留と確認用データを保存 | 自動発行不可 |
| 保留中に正常な再通知 | 商品・数量・入金状態の候補と変更履歴だけ保存 | 管理者承認まで発行権を作らない |
| 商品・数量が保存済み権限と違う | 保存済み注文・権限を上書きする前に保留し、差分を記録 | 自動承認不可 |
| 保留中の既存権限 | 消込状態・発行済み原本を保持 | 新しい発行を停止。購入済み原本URLの閲覧は変更しない |
| 管理者承認 | 最新の候補の版と既存権限を照合 | 権限作成と保留解除を同じトランザクションでコミット |
| 同じ承認の再送 | 承認済みの同じ版なら成功を返す | 発行権を再作成しない |
| 既に処理した同一ソース通知の再取得 | 記録済みフィンガープリントでスキップ | 承認後に同じ古い通知で再保留しない |

Payhip・STORES・Etsyに共通の承認サービスを追加した。商品コードの新規有効化・価格・占術計算・YAML内容は変更していない。運営メールは今回変更・再送していない。

## 承認の操作と検証

管理画面の保留一覧から注文を選択し、「明細・既存発行権・変更履歴を確認」で詳細を取得する。購入内容の確認チェックと注文IDの入力後に承認する。

- `GET /internal/orders/holds/{provider}/{order_code}`: 既存管理認証で確認用データ・既存権限・履歴を取得。購入者氏名・メールアドレス・注文本文・出生情報は返さない。
- `POST /internal/orders/holds/{provider}/{order_code}/approve`: 設定済み管理トークン必須。ローカルアクセスだけで承認できる例外は設けない。
- リクエストは`confirm_order_code`と`review_version`のみ使用。クライアントが任意の商品・数量を指定して発行権を作る方式ではない。
- 確認後に商品・数量・入金状態・保留理由が変わった場合は`REVIEW_CHANGED`で拒否する。UIは再確認を求め、勝手に再承認しない。
- 購入根拠のない候補、未登録コード、商品とSKUの不一致、未入金、不正な数量、重複明細は承認しない。
- 既存権限の商品の差し替え・削除、既存発行済みチャート数より小さい数量への変更は拒否する。既存権限と一致する部分を維持し、管理者が承認した不足分のみ追加する。
- 保存・解除・コミットの失敗時はロールバックする。コミットの応答が不確実な場合は、最新状態を確認して同じ版を再送できる。

未分類Etsy注文を管理者が商品名だけで推測して承認する機能はない。検証済みの商品コードを含む購入根拠が必要。既存権限の差し替えや取消が必要な注文は、この承認機能とは別に調査・明示的な対応が必要。

## トランザクション・再送

通常同期・承認・原子的な発行の入口で、スキーマ・販売サイト・注文IDから生成した同じトランザクションアドバイザリロックを取得する。承認は保留行・既存権限にも`FOR UPDATE`を使用し、発行権の既存一意制約と`ON CONFLICT DO NOTHING`を維持する。

保留状態の発行前検査は、発行権テーブルがない旧方式へのフォールバックより前にも行う。承認だけでチャートを生成することはなく、その後の購入者による発行は既存の原子的な消込経路を使用する。

`marketplace_processed_notices`には、販売サイト・注文ID・通知フィンガープリント・処理時刻だけを保存する。フィンガープリントはソースMessage-IDと購入判断フィールドのハッシュ。メール原文・元のMessage-ID・購入者情報は保存しない。同じIDでも商品・数量等が変われば別通知として扱う。通知の記録と注文処理は同じトランザクションなので、失敗時に記録だけが残って処理を失う設計ではない。

Message-IDがない入力については同一通知と断定せず、保守的に再処理する。この場合、承認後の古い不正通知で再保留になる可能性があるが、自動発行・自動解除はしない。新しいソースIDの不正通知も再保留の対象。

同時実行に対する上記の防止処理は実装済みだが、**実PostgreSQLでの競合結果はまだ検証していない**。モックの成功から実DBの合格を推定しない。

## DB変更（未適用）

`services/order_holds.py::DDL`と`scripts/sql/create_marketplace_order_holds.sql`を更新した。

- 既存保留表に`candidate`、`review_version`、`review_history`、`approved_version`、`approved_at`を追加。
- 処理済み通知表`marketplace_processed_notices`を追加。

`CREATE TABLE IF NOT EXISTS`と`ADD COLUMN IF NOT EXISTS`で既存の保留記録を保持する。新しい起動時DDL経路は追加していない。明示的な既存初期化処理の定義を更新しただけで、本番・テストDBへの適用は行っていない。

旧保留データに候補がない場合は、そのまま承認できない。正常な通知の再取込で候補を確認してから承認する。公開時にはDDLとコードを整合させる必要があり、旧コードと新コードの混在中まで管理者承認必須を保証するものではない。今回デプロイは行っていない。

## テスト結果

旧XFAILは通常の成功テストへ変更し、3販売サイトで正常な再通知が自動解除・自動権限作成をしないことを確認した。

限定回帰: **140成功、13未実施、XFAILなし**（0.89秒）。Python構文、管理画面JavaScriptの構文、DDL資料とコード定義の一致、`git diff --check`も確認した。SQLの実行・ブラウザでの実DBを使う承認操作は未実施。

実DB検証は元の7件を維持し、以下の6件を追加して合計13件を用意した。専用の隔離DB接続先が未指定のため、全てSKIPであり合格として数えない。

1. 有効な再通知で保留が残り、承認後だけ発行可能。
2. 6並列の管理者承認でも確定した枠数だけ作成。
3. 確認後に変わった明細の古い版を拒否し、履歴を保持。
4. 権限作成後の解除失敗で権限・保留状態をロールバック。
5. 既存原本を維持し、保留中の追加発行を止め、承認後の不足枠のみ発行。
6. 同一ソースの旧通知を再取得しても承認済み注文を再保留・増枠しない。

全体回帰の最終結果は**2166成功、13未実施、161 subtests成功、XFAILなし**（98.45秒、5653 warnings）。同ディレクトリの`order_hold_admin_approval_evidence_20261011.json`に記録した。途中の全体2163成功・12未実施は通知再取得の追加補強前の結果であり、最終結果と合算しない。
