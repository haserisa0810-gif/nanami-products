# nanami-products 占術計算 独立レビュー（Claude Opus 5.5）

**前提**
- このレビューは、渡された固定スナップショットを読んだだけで書いています。ツールでの資料閲覧、テストやコードの実行、DB参照はしていません。
- 「確認済み」は、コードを読んだ結果と手計算・代数で導いた結論です。実行して確かめたものではありません。
- 暦の基準日（2000-01-01＝戊午日、1949-10-01＝甲子日）は記憶に基づきます。2つは互いに整合しますが、外部資料では未照合です。
- 既存テストの合格や実装コメントは根拠に使っていません。
- `prompt_builder.py`、`output_metadata.py`、UI、年抽出プロトタイプは今回の資料にないため未検証です。

## 1. 総評

- 次の表と規則は、手で照合して正しいことを確認しました。
  - 干支表、十神、十二運表（陰干逆行・火土同根）、空亡
  - 六合・冲・害・破・刑・三合、天乙・文昌・天徳
  - 年柱（立春）、月柱（節入り）と五虎遁・五鼠遁、大運の順逆規則
- **公開を止めるべき欠陥が1件あります（P0）。** UTCオフセットが0以下の地域（英国の冬時間、UTC、南北アメリカ）で出生した場合、日柱が1日ずれます。時柱と以降の派生値もすべて連動して誤ります。国内（JST）は正しく出るため、国内例だけのテストでは見つかりません。
- **P1は7件です。**
  - 日替わりオプションの意味と出力ラベルが矛盾している
  - 性別不明が黙って女性扱いになる
  - 旧来の身強スコアの判定欠落と尺度の偏り
  - 夏時間の扱いが開示されていない
  - 時刻不明時、トランジットに確定値のようなハウスが出る
  - 小惑星APIにタイムゾーンを送っていない（仮説）
- 用神・身強を五行の個数だけで確定する処理は**ありません**。新しい構造分析は重み付きの候補提示にとどまり、時柱が不明なら保留します。ただし旧来の `features.strength` は判定ロジックに欠陥があり、そのままAIに渡されています。

## 2. 検証した式・条件

| 項目 | 独立に用いた式・条件 | 結果 |
|---|---|---|
| 日干支 | 正しい値は `(JDN + 49) mod 60`（0＝甲子）。Python では `(date.toordinal() + 14) % 60`（JDN = ordinal + 1721425 から導出） | 1975-09-15→甲子、1949-10-01→甲子、2000-01-01→戊午で互いに整合。実装式の挙動は §3 F1 |
| 実装の日干支式 | J = 現地0時のUTCでのJD = N − 0.5 − h/24（hはUTCオフセット）。これを `int((J+0.5+50)%60)` に入れると N+50−h/24 の切り捨てになる | 0<h<24 なら N+49 で正しい。h≤0 なら N+50 で**+1日ずれる** |
| 年柱 | `(y−4) mod 60`、立春（太陽黄経315°）前は y−1 | 正しい |
| 月柱 | `floor(((λ−315) mod 360)/30)`、五虎遁 | 正しい（丑月は前年の年干で計算） |
| 時柱 | 五鼠遁（甲己→甲子、乙庚→丙子、…） | 表は正しい。23時台の扱いは F3 |
| 十二運 | 陽干順行・陰干逆行、戊=丙・己=丁 | 10干すべての位置を照合し一致 |
| 大運 | 陽年男・陰年女＝順行。節（30°境界）までの日数×（3日=1年） | 規則は正しい。性別の既定値は F4 |
| 旺相休囚死 | 月令と同じ五行=1.5、月令が生じる=1.2、月令を生じる=1.0、月令を剋す=0.8、月令に剋される=0.6 | 順序は正しい（係数は独自のもの） |
| 接近・離反 | `rate = d|sep|/dt`。偏差が正なら rate<0 で接近、負なら rate>0 で接近 | 0°・180°付近の符号反転も含め正しい |
| 神殺 | 甲戊庚→丑未 ほか（天乙）、文昌・天徳の口訣 | 一致（庚辛→寅午とする流派差あり） |

## 3. 発見事項

### F1【P0】UTCオフセットが0以下の地域で日柱が+1日ずれる
- **分類**：計算エンジン
- **箇所**：`services/shichusuimei_calc.py:471-476`
- **最小入力**：`day_kanshi_from_birth(datetime(2000,1,1,12,0), tz_name="Europe/London")`
- **期待と実際**
  - 期待：戊午
  - 実際（予測）：己未
  - 同じずれが起きるもの：`UTC`、`America/New_York`、`America/St_Johns`（−3:30）、ロンドンの冬時間
  - 正しく出るもの：`Asia/Tokyo`、`Pacific/Kiritimati`、ロンドンの夏時間（BST、+1）
- **根拠（確認済み・代数）**
  - 現地0時をUTCに直したJDは N−0.5−h/24 です。
  - これを `+0.5+50` して切り捨てると、h>0 のとき N+49、h≤0 のとき N+50 になります。
  - UTCでは J = 2451544.5 なので、2451595 mod 60 = 55（己未）です。
- **影響**：日主が変わるため、時柱・十神・十二運・空亡・神殺・構造分析がすべて誤ります。`yaml_exporter` は海外出生の入力に対応しているため、到達しうる経路です。
- **再現**
```python
from datetime import datetime, date
from services.shichusuimei_calc import day_kanshi_from_birth, KANSHI_60
ref = lambda d: KANSHI_60[(d.toordinal() + 14) % 60]   # 独立式
for tz in ["Asia/Tokyo", "Pacific/Kiritimati", "UTC", "Europe/London", "America/New_York"]:
    for d in (date(2000, 1, 1), date(2000, 7, 1)):
        got = day_kanshi_from_birth(datetime(d.year, d.month, d.day, 12, 0), tz_name=tz)
        print(tz, d, got, ref(d), "NG" if got != ref(d) else "")
```
- **修正案**：タイムゾーンに依存しない現地暦日から直接求める。`KANSHI_60[(local_date.toordinal() + 14) % 60]`
- **旧データへの対応**：旧データは変更しないでください。保存済みの入力タイムゾーンを読むだけで、影響を受けた注文を抽出できます。顧客への告知が必要かは別途判断が必要です。

### F2【P1】`day_change_at_23` の実際の挙動が出力ラベル「23:00切替」と矛盾
- **分類**：方式・流派差、および商品出力
- **箇所**
  - 挙動：`shichusuimei_calc.py:440-446`
  - ラベル：`:1393-1396`（「23:00 切替設定を使用」）
  - 別ラベル：`:1671`（「子刻後半を前日扱い」）
- **最小入力**：ONで 1999-12-31 23:30 と 2000-01-01 00:30（いずれもJST）
- **期待（標準的な23時切替）**：どちらも 戊午日・壬子時
- **実際（予測）**：どちらも 丁巳日・庚子時
- **根拠（確認済み）**
  - ONのとき、23時台は暦日のまま、0時台は前日扱いになります。
  - 結果として「1:00に日が替わる」規則になり、子刻全体が標準の23時切替より常に1日前に置かれます。
  - 同じ出力の中に2種類のラベルが混在し、AIに誤った前提を伝えます。
- **再現**

```python
from datetime import datetime
from services.shichusuimei_calc import pillars4
for dt in (datetime(1999, 12, 31, 23, 30), datetime(2000, 1, 1, 0, 30)):
    print(pillars4(dt, day_change_at_23=True))
```
- **修正案（提案のみ）**
  - 現在の挙動を残すなら、名称とすべてのラベルを「子刻を前暦日に属させる」に統一する。
  - 標準の23時切替を別のオプションとして追加する（23時台は翌日の日柱と、翌日の子時の干）。

### F5【P1】旧来の身強スコア：食傷月を中立扱い、「弱め」がほぼ出ない尺度
- **分類**：計算エンジン（独自係数ではなく実装の矛盾）
- **箇所**：`shichusuimei_calc.py:739-752`、`:786-794`、`:800-805`
- **問題1：食傷月が中立になる**
  - 五行の関係は「同・生じられる・生じる・剋す・剋される」の5種類で、中立という関係は存在しません。
  - 実装では「日干が月令を生じる（食傷＝洩気）」の分岐が欠けているため、else の「中立 0点」に落ちます。
  - 例：甲日・午月 → `得令(中立)`
  - 同じファイルの `_build_structure_report` は5関係すべてを扱っており、ファイル内で矛盾しています。
- **問題2：尺度が強い側に偏っている**
  - 十二運の点数は常にプラス（最低でも+1）です。
  - 減点は得令の −12 しかありません。
  - 「弱め寄り（40以下）」になるには、官殺月・根なし・透干なし・十二運の合計7以下がすべて揃う必要があります。
- **反例（実在する日時）**：1996-08-25 15:30 JST
  - 命式：丙子年・丙申月・甲午日・壬申時（独立式で日柱＝甲午、五虎遁で丙申、五鼠遁で壬申）
  - 予測される計算：50 − 12 + 0（通根なし）+ 0（透干なし）+ round((4+1+3+1)/3)=3 → **41点「中庸寄り」**
  - 申月の甲木で根がない命式は、扶抑の観点では通常「弱い」と読まれる典型例です。
  - 参考：新しい構造分析を手計算すると支持比率 ≈ 0.44（balanced）です。印（水）の重みが反映されるため、こちらは流派判断の範囲に収まります。
- **再現**
```python
from datetime import datetime
from services.shichusuimei_calc import pillars4, _calc_strength_score, Pillars4
p = pillars4(datetime(1996, 8, 25, 15, 30), tz_name="Asia/Tokyo")
print(p, _calc_strength_score(p))   # 予測: 丙子/丙申/甲午/壬申, score=41
print(_calc_strength_score(Pillars4("庚午", "壬午", "甲子", "甲子"))["breakdown"][0])  # 合成例: 得令(中立)
```
- **修正案**
  - 食傷の分岐を追加する。
  - スコアを中心0の符号付きにする。
  - 旧来キーをAIへ渡すときは「参考値・非推奨」と明示する。

## 6. 公開判断に必要な追加検証
1. **日柱**：同じライブラリでの照合ではなく、独立した根拠と比べる。
   - 印刷版の万年暦、または国立天文台の暦と照合する。
   - 独立式 `(ordinal+14)%60` で、全タイムゾーン（−12〜+14、30分刻みのオフセットを含む）×複数の日付を総当たりで比較する。
2. **節気時刻**：国立天文台『暦要項』の二十四節気時刻と、±1分以内で一致するか確かめる（1950〜2050年の立春と12の節）。
3. **天体位置**：JPL Horizons で照合する。Swiss Ephemeris とは別のソフトウェアです。ただし元データ（DE系列）は共通なので、完全に独立した検証ではない点に注意してください。
4. **ASC/MC**：手計算と照合する。`tan ASC = −cos RAMC / (sin ε tan φ + cos ε sin RAMC)`
5. **方針決定**：日替わり、23時台の時干、夏時間、真太陽時、性別不明時の扱いを決め、assumptions に明記する。
6. **テストの固定日時**：現在時刻に依存する箇所は、すべて固定日時で検証する。
   - `as_of` と `transit_start_date` に `datetime(2026,10,10,12,0,tzinfo=ZoneInfo("Asia/Tokyo"))` を渡す。
   - `generated_at` は比較対象から外す。
7. **旧購入データと原本**：変更・再生成をしないでください。
   - 修正は `engine_version` を上げて、新規発行分にだけ適用する。
   - 影響の調査は保存済み入力を読み取るだけにとどめる（F1は海外のタイムゾーン、F2はONの利用、F4は性別不明の注文）。
