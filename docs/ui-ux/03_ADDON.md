# Add-on UI/UX仕様書

## 1. 位置づけ

Add-onは、購入者がすでに持つ基本版／FULL版等の計算済みデータへ、小惑星、31日トランジット、長期トランジット等を追加する別売商品である。ベースYAMLや鑑定URLは計算元であり、通常のAdd-on購入証明ではない。

発行権、販売元、数量、DB、旧注文fallbackの正本は `docs/MULTI_PURCHASE_ORDER_ENTITLEMENTS_SPEC.md` とする。本書は購入者が見る画面と操作の受入条件を定める。

## 2. 正規の3ルート

### 2.1 有効な鑑定URLから進む

1. 鑑定結果の「次のトランジットを作成」等から `/addon/new` へ遷移する。
2. `previous_chart_url` からベースデータをサーバーが読み込む。
3. 購入者は別途購入したAdd-onのオーダー番号を入力する。
4. 発行権を1枠消費し、新しい結果URLを発行する。

ベース鑑定の販売元をAdd-onの購入元として推測しない。表示言語だけを引き継ぐ。

### 2.2 保存YAMLを貼り付ける

1. 元URLが期限切れ、または利用できない場合に選ぶ。
2. 購入者が保存済みの基本版／FULL版YAMLを貼り付ける。
3. 別途購入したAdd-onのオーダー番号を入力する。
4. ベースYAMLの形式・商品適合性を確認後、発行する。

過去購入者のv1 YAMLと現行v2 YAMLを継続して受け付ける。

### 2.3 note特典

- `/note-transit/{access_key}` から提供する期間・企画限定の特典ルートである。
- 通常販売Add-onのオーダー番号消費とは分離する。
- アクセスキーの有効範囲、期間、回数に従い、通常注文の発行権を勝手に作成・消費しない。

## 3. フォーム表示

- 通常時は販売元プルダウンを表示しない。
- 共通入力名は「オーダー番号」とし、「STORESオーダー番号」のような特定店舗限定表現を使わない。
- EN / ES / DEでは、同じ意味の一般的な注文識別ラベルを表示する。
- サーバーは発行権を消費しない照合で対応販売元を横断検索する。
- 一意に一致した場合は販売元を自動採用する。
- 未一致時は許可されたメール同期を1回だけ行い、再照合する。
- 異なる販売元で同じ入力が同じAdd-on商品に一致した場合だけ、一致候補に限定した販売元選択を表示する。
- Gumroadは現行Add-on自動照合の対象外とする。
- 過去のCoconala販売は新規販売停止済みだが、既存購入者互換の照合を削除しない。

## 4. 商品適合性と数量

- 選択したAdd-on SKUと注文明細の商品が一致しなければ発行しない。
- FULL版、基本版、ACG等の本体商品注文番号をAdd-on購入証明として流用しない。
- 数量2なら独立した発行権を2枠用意し、1回目の生成後も残枠を使える。
- 同一注文に異なるAdd-onがある場合、SKU／明細単位で別々に消費する。
- 同時送信でも同じ枠を二重消費しない。
- 生成途中で失敗した場合、発行権だけが失われない原子性を維持する。

## 5. 成功・再訪

- 統合型Add-onは新しい `/chart/{token}` へ進む。
- 専用トランジット型は `/addon/transit/{token}` または `/addon/long-term-transits/{token}` へ進む。
- 言語を生成結果へ引き継ぐ。
- 同じ注文番号で再訪した場合、既存結果と残枠を区別して案内する。
- 複数結果がある場合、単一の「前回結果」で上書きせず、購入者が選べる一覧または明確な個別リンクを返す。
- 専用ページの期限切れはHTTP 410と画面案内を一致させる。

## 6. エラー仕様

| 状態 | 表示・動作 |
|---|---|
| オーダー番号未入力 | 入力欄を示し、ベースデータは保持 |
| ベースURL無効／期限切れ | YAML貼り付けルートを案内 |
| YAML形式不正 | 内部パーサ例外を出さず、保存済み正規YAMLを貼るよう案内 |
| 商品違い | 選択Add-onと購入商品が一致しないことを表示 |
| 未一致 | 入力確認と問い合わせ方法を表示。全販売元の内部検索結果は表示しない |
| 販売元衝突 | 一致した候補だけを選択肢として表示 |
| 枠枯渇 | 追加生成不可と既存結果への導線を分ける |
| 生成失敗 | 再試行可否を案内し、枠の状態を不整合にしない |

## 7. 受入テスト

### 自動テスト

- URL引継ぎ、YAML貼付、note特典の3ルートを別々に検証する。
- 通常時に販売元プルダウンが出ず、衝突時だけ候補が出る。
- 各販売元で一意判定、未一致後同期、衝突、商品違いを検証する。
- 数量2、異なるSKU、部分使用、枯渇、同時送信を検証する。
- v1／v2 YAMLを受け付け、不適合な商品YAMLを拒否する。
- JA / EN / ES / DEの入力ラベル、エラー、結果URLを確認する。
- 通常注文の発行権とnote特典の状態が干渉しない。

主なテスト: `tests/test_multi_purchase_entitlements.py`, `tests/test_addon_idempotency.py`, `tests/test_addon_generate_product_mismatch.py`, `tests/test_long_term_transit_addon_form.py`, `tests/test_note_transit.py`, `tests/test_transit_addon_prompt_equivalence.py`。

### 手動テスト

- 有効なFULL版URLから遷移し、ベースYAML貼付欄が不要な状態で発行できる。
- URLが使えない想定でYAML貼付へ切り替えられる。
- スマートフォン幅で長いオーダー番号、エラー、衝突時プルダウンが崩れない。
- 実販売メールを使う試験は難しいため、専用テスト注文とDBの期待状態を事前に固定する。
