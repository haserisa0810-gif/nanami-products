# 複数購入・発行権管理仕様（Etsy / STORES / Payhip）

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 決定日 | 2026-08-27（JST）。2026-08-28に販売元を含む注文識別を追加 |
| 対象 | Etsy、STORES、Payhipの注文番号引換フロー |
| 実装状態 | ローカル実装・自動テスト済み。本番未デプロイ、DB未変更 |
| 本番操作 | 別ターンの明示承認があるまで禁止 |

### 1.1 販売元の運用状態（2026-08-28追記）

- 現行販売・新しい複数購入対応の対象はEtsy、STORES、Payhipとする。
- ココナラでの新規販売は終了した。
- ココナラの既存URL、既存DB注文、購入者名照合、管理者サポート経路は、過去購入者のためLegacy互換として維持する。
- ココナラを新しい発行権方式へ移行せず、複数購入の新規保証対象にも含めない。過去の同一購入者による複数購入に問題がある場合は個別サポートで扱う。

## 2. 背景と決定

従来は `redemptions.order_code` が主キーであり、1つの注文番号につき1回だけ発行できた。このため、同じ注文で数量2を購入した場合や、複数商品を同時購入した場合、最初の1件を発行した時点で注文全体が使用済みになっていた。

この問題は言語固有でもEtsy固有でもない。Etsy、STORES、Payhipを共通して、次の単位で発行権を管理する。

```text
購入元 + 注文番号 + SKU/商品明細 + 明細内の個数
```

- 数量2なら発行権を2件作る。
- 同じ注文に異なる商品があれば商品ごとに発行権を作る。
- 同一SKUが複数明細に分かれる場合は、出現順の明細番号で区別する。
- `NP-WF-ES`、`NP-WF-DE`等のSKUは発行権の識別情報として保存する。
- 購入言語によるフォーム制限は行わない。ES購入者がDE表示で発行することも、その逆も許容するという既決事項を維持する。

## 3. データ設計

既存の `stores_orders`、`redemptions`、`charts` は削除・置換しない。新しい `nanami_products.marketplace_orders` と `nanami_products.order_entitlements` を追加する。

### 3.1 注文ヘッダー

`marketplace_orders` の主キーは `(provider, order_code)` とする。同じ文字列の注文番号がEtsy、STORES、Payhipの複数社で発生しても、別注文として保存・照合する。既存の `stores_orders` は後方互換用のミラーとして残すが、異なる販売元の同一番号で既存行を上書きしない。

起動時に既存 `stores_orders` を `marketplace_orders` へ非破壊でコピーする。販売元が空の旧行はSTORESとして扱う。過去に異なる販売元の行で上書き済みの情報は、旧テーブルだけからは復元できない。

### 3.2 発行権

主な列:

| 列 | 用途 |
|---|---|
| `provider` | `etsy` / `stores` / `payhip` |
| `order_code` | 販売元の注文番号 |
| `line_item_key` | SKUまたは商品種別と明細出現番号から作る安定キー |
| `sku` | `NP-WF-ES`等。言語制限には使用しない |
| `product_type` | `western_full`等、発行フォームとの商品整合確認に使用 |
| `unit_index` | 数量内の1件目、2件目… |
| `status` | `available` / `redeemed` / `revoked` |
| `chart_token` | その発行権で生成した既存チャート |

一意制約は `(provider, order_code, line_item_key, unit_index)` とする。メールを再同期しても同じ発行権を重複作成しない。

## 4. メール取込

`services/stores_mail_sync.py` が3社の通知本文から商品行、SKU、`個数` / `数量` / `Qty` / `Quantity` を抽出する。数量は安全上1〜100に制限する。明細情報がない旧形式は、従来の商品判定結果を数量1として扱う。

取込結果は `marketplace_orders` へ `(provider, order_code)` 単位でupsertし、発行権を明細・数量単位で作成する。後方互換用 `stores_orders` への反映は、既存行と販売元が同じ場合、または旧行の販売元が空の場合だけ行う。

既存注文を再同期した際、すでに `charts` に保存された結果があれば、同じ販売元・注文番号・商品種別の発行権へ対応づけて使用済みにする。販売元未保存の旧チャートをSTORESとして扱う互換は維持するが、Etsy／Payhipへのbackfillでは販売元未保存チャートを使用しない。既存チャートURLと `redemptions` は変更しない。同じメールの再同期も冪等である。

## 5. 発行と同時実行

発行時は、`marketplace_orders` の対象注文と、対象の `provider + order_code + product_type` に一致する未使用枠を照合する。未使用枠は `FOR UPDATE SKIP LOCKED` で1件確保し、次を同じDBトランザクション内で行う。

1. 発行権を `redeemed` にする。
2. `chart_token` を関連づける。
3. チャートを保存する。
4. 初回のみ従来の `redemptions` 行を作る。2件目以降は同じ行を増やさない。

チャート保存が失敗した場合は発行権の消費もロールバックする。同時に複数送信されても、同じ枠を二重利用しない。

管理者の既存 `reset_once` は維持する。照会・リセットは販売元を必須選択し、`provider + order_code` の対象だけを操作する。対象注文がリセット状態なら、使用済み枠を再発行に使い、成功後に状態と代表トークンを更新する。管理画面の対象販売元はSTORES、Etsy、Payhip、および過去購入者サポート専用のココナラである（ココナラは発行権方式ではなく既存の単品方式）。

## 6. 再訪時の購入者体験

- 発行結果が1件だけなら、従来どおりその結果へ直接移動する。
- 発行済みがあり、同じ商品の未使用枠もある場合は、勝手に次の枠を消費せず、発行済み一覧を表示する。
- 一覧の「残りの購入分を発行する」からフォームへ戻った場合だけ、次の枠を使う。
- 2件以上発行済みなら、注文の発行済み結果一覧を表示し、各結果を個別に開ける。
- 一覧UIはJA/EN/ES/DEに対応する。
- 発行済みチャートの検索も `provider + order_code + product_type` で絞り、別販売元の同一注文番号や別商品を同じ一覧へ混ぜない。

注文番号はURLへ新しい公開結果ページとして固定保存せず、注文照合後のレスポンス内で一覧を表示する。個々の結果は従来のランダムなチャートトークンURLで開く。

## 7. 後方互換性

- 発行権行がない旧注文は従来の注文番号単位の動作へフォールバックする。
- `marketplace_orders` がない移行前環境では `stores_orders` を販売元条件つきで参照する。
- 既存の `stores_orders`、`redemptions`、`charts` と既存チャートURLを維持する。
- 単品・数量1の新規注文は、見た目上これまでと同じである。
- SKUの言語サフィックスは保存するが、購入言語をDBへ必須保存せず、表示言語の相互利用を妨げない。
- 販売終了済みのココナラ、Gumroad、管理者生成、Personal Editionコードは今回の新しい発行権方式へ移行せず、既存動作を維持する。ココナラは過去購入者のLegacy引換・サポートに限る。
- Etsy/STORES/Payhipで購入されたaddon SKUは数量分の発行権を使う。FULL、基本版、ACG等の本体商品注文番号をaddon購入証明としては使用しない。旧addon注文に発行権行がない場合だけ、保存済みの商品種別が選択したaddon種別と一致することを確認して `addon_redemptions` を使用する。

### 7.1 トランジットAdd-onの3つの正規ルート

1. 有効なFULL版等の鑑定URLから「次のトランジットを作成」へ進み、計算元データをURLから引き継ぎ、別途購入したaddon商品の注文番号を消し込んで新しいURLを発行する。
2. 元の鑑定URLが期限切れ等で使えない場合、購入者が保存していた基本版／FULL版YAMLを貼り付け、別途購入したaddon商品の注文番号を消し込んで新しいURLを発行する。
3. note特典は秘密のキャンペーンURL自体を発行権とし、基本版／FULL版のURLまたは保存YAMLを計算元にする。販売元の注文番号と `order_entitlements` は使用しない。

いずれもURLまたはYAMLは計算元データであり、通常販売のaddon購入証明ではない。note特典以外では、基本版／FULL版／ACGの注文番号だけでaddonを発行してはならない。

鑑定結果からAdd-onフォームへ移動する際は表示言語を引き継ぐ。元鑑定の販売元とAdd-onの購入元が同じとは限らないため、元鑑定の販売元は継承しない。通常のAdd-onフォームでは販売元プルダウンを表示せず、注文番号、Order ID、または購入時のユーザー名を共通欄へ入力する。サーバーは発行権を消費しない照合で現行3社を検索し、過去購入者互換のためココナラ照合も残す。一意に一致した販売元を自動採用し、未一致時はメール同期を1回だけ実行して再照合する。異なる販売元に同じ購入情報が存在する場合だけ、一致候補に限定した販売元プルダウンを表示する。既存の `?provider=coconala` を含む購入者ガイドURLは過去購入者向けLegacyとして維持する。生成後の結果URLにもJA/EN/ES/DEの選択言語を引き継ぐ。Add-on非対応のGumroadは自動照合・選択候補の対象外とする。

## 11. 既知の制約と残る確認

- 手元の自動テストには実形式を模した通知本文と既存の実注文例を使っているが、3社すべての実際の複数明細通知はまだ候補環境で確認していない。公開前の必須確認とする。
- 過去のメールが同期取得範囲外の場合、その旧注文の数量は既存DBだけから復元できない。必要な旧複数注文は該当メールを再同期するか、個別移行手順を別途承認する。
- 既存の `stores_orders` は注文番号だけを主キーとしていたため、過去に同一番号の販売元衝突で保存されなかった、または上書きされた情報は自動backfillだけでは復元できない。候補環境で衝突監査を行い、必要な場合だけ元メールから再同期する。
- 販売元が通知メールの文言やレイアウトを変更した場合、明細解析fixtureの更新が必要になる。
- 鑑定元URLからAdd-onの購入元は推測しない。共通購入情報をDBで販売元横断照合し、通常は自動判定する。異なる販売元で同じ入力が同じAdd-on商品に一致した場合だけ購入者の選択が必要になる。
- 本番デプロイ、本番DBマイグレーション、Etsy/STORES/Payhipの公開設定変更は行っていない。
