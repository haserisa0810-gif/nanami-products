# 設計メモ: 出生時刻の修正・再発行（時刻探索）

決定日: 2026-07-14（西洋深化ロードマップ議論の派生）
状態: 方針確定・実装は西洋深化ステップ2（YAML v2）以降

## 背景

YAML v2 で `time_sensitive_provisional`（時刻依存値の隔離）と
`recalculation_required_when_time_known: true` を導入すると、
商品自身が「時刻判明時は再計算が必要」と顧客に伝えることになるため、
再計算の出口が必要になる。また「後から母子手帳等で時刻が判明した」は
占い購入者に実際に多いケース。

## 確定した方針

- **修正できるのは出生時刻のみ**。生年月日・出生地は不変
  （変更を許すと別人のチャートを無料入手できてしまい商品として崩壊するため、境界はここ）
- 修正は**ベースチャート側の一級操作**として実装する。アドオン購入時の
  パラメータにはしない（旧時刻ベース＋新時刻アドオンの矛盾YAMLペアが
  顧客の手元に残り、AI鑑定の品質事故になるため）
- アドオンはベースYAMLから出生情報を読む既存設計のため、
  修正済みベースを貼り直せば自動的に新時刻で計算される（追加実装ほぼゼロ）

## 探索と確定の分離

「自分に合いそうな時刻を探す」使い方（簡易レクティフィケーション）を許容する。

- **探索 = プレビュー**（保存なし・回数無制限）:
  候補時刻を入力すると ASC/MC・月星座・ハウス配置の変化をその場で表示。
  YAMLは発行せず、DB書き込みなし
- **確定 = 再発行**（回数制限つき。初期値: 3回を想定、要最終決定）:
  同一トークンに新バージョンのYAMLを発行。納品済みの旧YAMLは書き換えない。
  YAMLに `correction_history`（旧時刻→新時刻・実施日時）を残す
- 表示条件: `birth_time_accuracy != exact` のチャートのみ（exact購入者には出さない）

## 段階分け

1. **今**: 実装しない。ポリシーのみ（本メモ）
2. **YAML v2 実装時**: `/chart/{token}` に「出生時刻が判明した場合はこちら」の
   案内文＋問い合わせ導線を追加。実際の再生成は管理者フローで対応
3. **問い合わせが発生し始めたら**: セルフサーブのプレビュー＋再発行UIを実装

## 未決事項

  （アドオン注文番号は使用済みのため、同一注文番号での再生成を許すか。
  MVPでは管理者対応に逃がす）
- ACG への時刻精度伝播（GPT議論で指摘済み。時刻不明時は ASC/DSC/MC/IC 線を
  非表示または警告。再発行時はACGも新時刻で引き直しになる旨の案内）

## 段階2の実装状況（管理者向け）

出生時刻の修正依頼を受けたら、管理者用YAML生成フローを使用する。
元の納品と同一の生年月日・出生地を入力し、判明した正確な出生時刻だけを変更して再生成する。
生成された新しいトークンURLを顧客へ案内し、旧チャートは履歴として削除せずに残す。
生年月日または出生地も異なる場合は時刻修正として扱わず、個別に確認する。
セルフサービス再発行は未実装のため、当面は公式LINE経由の管理者対応とする。
