## 変更内容

### 通常商品・追加商品の消込直前チェック

`services/pg_store.py` の通常商品の消込処理を追加商品でも利用するようにした。注文単位のトランザクションアドバイザリロックを先に取得し、保留状態を確認する。その後、保存された購入状態と商品コードの完全一致を確認し、利用可能な発行権を行ロックして、条件付きUPDATEで1枠だけ消費する。追加商品の旧注文の消込にも同じ保留チェックを適用する。

通知取込・管理者承認・通常消込・追加消込で、注文ロックを行ロックより先に取得する順序を揃えた。確認から消込・結果保存まで同一トランザクションに留める。新しい排他機構やテーブルは追加していない。

保留注文は `held`、未入金の注文は `unpaid` として書き込み前に停止する。発行済み原本を読むURLの処理は変更していない。

維持した商品別の処理：

| 経路 | 保存・消込方式 |
| --- | --- |
| 通常商品 | redemptions と charts を同一トランザクションで保存 |
| 小惑星追加 | 発行権消込と charts 保存を同一トランザクションで実行 |
| 31日・長期トランジット追加 | 消込と transit_addon_links、必要に応じた charts 保存を同一トランザクションで実行 |
| 四柱推命サイクル追加 | 消込のみ。既存どおりダウンロード応答を返し、原本の保存方式は追加しない |

通常商品の `reset_once` の再発行は維持した。追加商品は既存どおり、消費済み数量枠を `reset_once` によって再利用しない。旧追加注文へのフォールバックは同じ追加商品に発行権がない場合だけとし、保存済み商品種別との照合を維持した。明示的な reusable/test/permanent の扱いも維持し、保留中は消込を停止する。

### Payhipダウンロード通知

既存パーサーの `non_purchase_notification` 分類を維持し、`_upsert_order` でDB処理に入る前に分岐する。注文登録、発行権作成、保留作成、承認候補更新、購入通知の処理済み記録を行わない。同期結果ではスキップに数え、保留件数や新規保留通知に数えない。

監査は INFO ログに、販売サイト、通知種別、検証した注文識別子、メッセージIDのSHA-256を残す。メール本文、購入者情報、生のメッセージIDは記録しない。監査ログの保持・閲覧は運用環境のINFOログ設定に依存する。

同じメッセージIDで後から正常な購入通知が届いても、購入通知を処理できる。既存の保留通知再送処理は変更していない。

**過去に誤って保留された注文の自動解除は行わない。** 保存済み購入権限や保留の変更は運営者の確認が必要。保存済み原本の取得と期限確認は維持する。

### 実DBで確認した内容

- STORES・Payhip・Etsyそれぞれの保留注文：3追加経路、発行権あり・旧形式の双方で消込も結果保存も行わない。
- 通常商品と追加商品が同じ発行権を同時に消費する場合：成功は1件だけ。
- 4並列の追加商品消込：購入数量2件だけ成功し、残る処理と再実行は拒否。
- charts・transit保存の失敗：発行権を利用可能に戻すトランザクションロールバック。
- 追加商品の未入金注文と不一致SKU：発行しない。
- 管理者承認と追加消込の同時実行：デッドロックせず、承認前は保留、承認後も確認した数量のみ消費。
- 通常 `reset_once` は1回の再発行、追加 `reset_once` は消費済み枠を再利用しない。
- 購入前・購入済み・原本発行後・保留中・承認後のダウンロード通知：タイムスタンプを含む注文・権限・保留・候補・履歴・処理済み通知・原本のDBスナップショットが不変。
- ダウンロードと購入が同じメッセージID、または並列で到着：有効な購入だけを処理し、保留や発行権の増加は起こさない。

HTTP経路では保存済みPayhip原本の `.yaml` と `/prompt.txt` を取得でき、期限内200・期限外410を確認した。ここは保存取得だけをモックし、実DB検証とは区別する。実DB側でも発行済み原本の内容保持と残り数量の利用を確認した。
