前回Windows Device Guardに拒否されたPostgreSQL実行ファイルの再取得・再実行、アプリ制御ポリシーの変更、別パスへの移動による回避は行っていない。

PATH、Program Files、stagingの関連ディレクトリ、WSL状態、プロジェクト内の設定ファイル名、対象環境変数の存在だけを調査した。サービス一覧の照会は権限不足だったため、その照会だけからサービス不存在とは結論していない。SSHクライアントはあるが、承認されたテスト接続先・設定は見つからない。クラウド上にテストDBが存在しないとまでは断定しない。

## 管理者操作限定の反例

再現する入力はすべて架空:

1. Payhip `Order ID: AuditHeld / Product: [NP-SFULL]` を通常同期へ渡す。未登録コードとして保留する。
2. 同じ注文IDに対して `Product: [NP-WF]` の有効な購入通知を通常同期へ渡す。既存注文で発行権は未作成の状態とする。
3. 現在の処理は `_upsert_order_entitlements()` と `resolve_hold()` を呼ぶ。管理者操作は渡していない。

`tests/test_order_hold_retry_audit.py`にユーザー指定の「両処理が呼ばれない」という期待値を置いた。現状では違反するため`xfail(strict=True)`で記録した。**XFAILは品質要件の合格ではない。** DB呼出しはモックで、実PostgreSQLの状態遷移や商品の最終発行を実証した結果ではない。

コード上では購入者の注文検索時にも`STORES_MAIL_SYNC_ON_SUBMIT`（既定1）で通常同期が呼ばれるため、同期を常に管理者操作とみなすこともできない。

この反例は「未知コードのまま発行される」という意味ではない。後から有効な購入明細が届いた場合に、保留解除と権限作成が管理者承認なしで進むという運用条件の不一致。既存購入者の権限・原本を自動取消する提案でもない。

分類案: P1 / UI・購入導線（保留解除・発行権管理）。今回の範囲は検証のため、自動修正はしていない。公開前に、注文単位のロック下で保留中の自動権限作成・解除を止め、管理者が購入根拠を確認した操作に限定する方針を別途実装・検証する必要がある。現在の保留一覧APIは読取専用で、専用の管理者再処理操作は未実装。

メールだけの自動再送は別処理であり、5分間隔・pendingの再試行を維持する設計。SMTP成功後にDB更新が失敗した場合の重複通知の制約は残る。実DBでのロック・通知状態永続化、SMTP失敗後の実再送は未検証。
