# 容量のクラウド監視・確認待ち

実装ブランチ：`codex/capacity-monitor`。本番有効化は未実施。

## 動作

- 独立したCloud Run Jobが、JSTの3時・9時・15時・21時にPostgreSQLのDB全体サイズを集計する。Webサービスの画面やトラフィックは変更しない。
- READ ONLYを確認したトランザクションで`pg_database_size(current_database())`だけを読む。氏名・出生情報・注文番号・tokenは取得しない。SQL制限時間5秒・接続10秒・終了時rollback。
- 700MB超で注意、850MB超で緊急、集計失敗、12時間記録なしを既存のGoogle Cloudメール通知先「ナナミサポート」に通知する。正常時の定期メールは送らない。
- 700MB/850MBは暫定的な運用ライン。Neonの契約上限から求めた使用率ではない。契約と他ブランチ・復元履歴を含む利用量は、Neon接続後に別途確認する。DBのディスクサイズだけでプロジェクト全体の上限到達を保証して検知できるとは扱わない。
- 接続失敗時に容量ゼロを記録しない。ログには認証値・例外本文・顧客情報を出さない。
- 既存DB接続Secretの読み取り権限とMonitoringへの書き込み権限を、監視専用サービスアカウントに付与する。Scheduler用にはジョブ起動権限だけを付与する。

## 本番有効化に伴う操作

`scripts/activate_capacity_monitor.ps1`はclean・commit・push済みの状態を確認し、監視テストを再実行する。
以下はユーザーの本番監視有効化の承認後にだけ行う。

1. Scheduler APIの有効化、専用サービスアカウント2個と必要なIAM付与。
2. 小さな監視用コンテナのCloud Build / Artifact Registry保存。
3. Cloud Run Job作成・初回実行。
4. Scheduler1件とMonitoringアラート4件の作成または同名設定の更新。

Webサービスの`gcloud run deploy`、トラフィック切替、DBデータ更新・DDL・削除は含まない。
監視用ジョブには独立した有効化スクリプトを使う。アプリを公開する候補版ではないため、Web用`deploy_candidate.ps1`でアプリ全体を再配信しない。
正常な初回実行・メトリクスの記録・メール通知先・Scheduler状態を確認してから、稼働開始として報告する。
メール受信の実証は別途テスト通知が必要であり、設定の確認だけで実受信済みとは報告しない。

```powershell
.\scripts\activate_capacity_monitor.ps1 -Confirm 'ACTIVATE:nanami-capacity-monitor'
```

Cloud Schedulerは請求先アカウント単位で月3ジョブまで無料、超過は1ジョブ月US$0.10。Job実行・ビルド・イメージ保存・Monitoring・Neonの利用は別枠。
公式：https://cloud.google.com/scheduler/pricing
この処理は1日4回の小さな集計だが、追加費用が必ずゼロになる保証はしない。

## 期限切れ削除・試験発行の追加確認

- 削除APIは存在し、`grace_days=7`を明示した呼び出しなら期限から7日経過したものを対象にできる。既定値は0日であり、コード内に7日固定の自動実行はない。
- Googleプロジェクト`nanami-astro`と`nanami-astro-3bd74`でScheduler APIは無効。Neonにpg_cronとcron.jobはない。GitHubはmacOS検証と依存関係更新のみ。Codexの既存日次ヘルスチェックは読み取り専用。確認したWindowsタスクにも対象ジョブはない。
- 外部レポート用GCSバケットにもライフサイクルルールはない。ログ保持範囲内の直近180日指定検索で削除APIのアクセス記録は0件。保持期間外・別の外部システムまで否定できない。
- したがって、現時点では「期限から1週間後の自動削除が稼働している」と確認できない。重複した削除ジョブは作成しない。期限付き鑑定の現在の期限切れ件数は0件。
- 保存300件のうち注文番号なし34件、注文番号あり266件、引換記録への関連37件。明示試験フラグ/注文番号先頭の試験マーカー0件、試験を示す表示名候補13件。表示名による候補は確定分類ではない。注文番号ありも実売の証明ではない。
- 300件は販売実績ではなく保存件数。検証が本番へ保存した可能性はあるが、全件の発行元を示す統一した監査情報がないため、Codex/ClaudeCode由来の試験発行総数はこの集計だけで確定できない。試験だと推測して削除しない。

## PDFの方針

月100件ならまず、1台当たり同時生成1件の上限と月単位のPDFキャッシュを検討する。
キャッシュキーには原本ハッシュ・対象月・言語・祝日国・レンダラーの版を含める。購入者ごとに元データが異なるため、他人のPDFを返さない設計を回帰テストする。
個人情報を含むPDFは非公開で保存し、ダウンロード時にURL有効期限を再確認する。公開バケットを使わない。
待ち時間が許容できなければ、PDF生成専用のジョブ/サービスへ分離し、閲覧用CPUとの競合を避ける。単に最大台数を増やす方法だけに頼らない。
PDFのコード・本番への変更は今回まだ実施していない。
