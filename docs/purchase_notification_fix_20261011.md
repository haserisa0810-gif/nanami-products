## 購入明細の根拠

本文全体や件名に現れるコードは購入権限の根拠にしない。対象フィールドのコードだけを共通商品台帳で完全一致照合する。

| 通知形式 | 採用するフィールド | その他の扱い |
|---|---|---|
| Payhip実通知 | `The following item(s) has/have been purchased:`の下、Order ID後からTotalまでの商品名＋通貨金額の行 | 商品名の既知コードを採用。ダウンロード見出しは購入扱いしない |
| STORES実通知（5件） | 番号付き商品行と、対応する`単価 x 個数 = 金額`行 | 小計・合計までの明細。金額・数量行が欠けた部分的な表は保留 |
| STORES旧通知（1件） | `注文商品：`直後の値 | この形式には注文情報より前に問い合わせ説明があるため、フィールド位置で判定 |
| 明示的な商品ラベル形式 | `Product:` / `Item:` / `商品：`等と数量フィールド | 案内・備考・おすすめ等のセクションへ入った後は採用しない |
| Etsyコードなし通知 | 明細があっても登録コードがない | 既定商品への振り分けを行わず、保留 |
| ココナラ既存形式 | 既存のタイトルフィールド | タイトルだけを照合。本文の案内コードは使用しない |

未登録コード・複数コードの曖昧な商品フィールド・不正な数量・不完全な購入表は、注文全体を保留し、新しい発行権を生成しない。正式な複数商品明細と複数数量は維持する。明細に数量表示がない既存の1商品行形式は、従来どおり1枠とする。対応外の通知形式を推測で補完しない。

MIMEのHTMLとplain textは同じ通知の別表現として扱い、plain textを優先して1つだけ読む。HTMLが先に現れるメールで双方を連結し、明細を二重計上することも防いだ。添付の案内文は明細に含めない。

## 実通知の回帰結果と前回報告の訂正

[実通知照合の集計](purchase_notifications_live_regression_20261011.json)は、原文メールに修正後のパーサーを適用した結果。対象はPayhip8件、STORES6件、Etsy1件の計15件。**すべて期待する分類・保留結果と一致した。**

前回「Payhipの注文通知8件」とした標本には、購入通知7件とダウンロード通知1件が含まれていた。構造の追加調査で判別したため、ここで訂正する。購入通知7件のうち5件は単一商品、2件は購入見出し配下の4商品明細。ダウンロード通知1件にも4コードがあるが、購入権限を生成しない。

期待値は修正後コードの出力からコピーせず、修正前に確認した標準見出し・商品行・金額行の構造とコードを固定して比較した。ただし販売側の注文APIや注文管理画面との独立照合は行っていない。実際の入金・返金の完全な照合を証明する検証ではない。

原文・注文ID・購入者情報は保存していない。回帰用JSONは注文ID・購入者・価格・商品名を架空値へ置換した最小フィールドであり、全文の匿名化コピーではない。実メールでの照合と匿名フィールドのローカルテストを区別している。

## Payhip入力・発行前チェック

- Payhipフォームの非空の未登録コードはエラーにする。NP-SFULL等をexpected_product_typeへフォールバックしない。
- 既存addon経路の空の任意コードは維持する。空欄から購入権限を生成する処理ではなく、指定商品と保存済み購入の照合は後段で必須。
- 原子的な発行権消込でも入金状態を検査する。
- 新しく保留された注文は発行権を持たないため、旧方式の「初回redemption」経路へ抜けて発行することを止める。
- 保存済みの既知商品・SKUなしの旧注文、明示的な再利用テスト注文の既存方針は維持する。

## 再通知と保存済みデータ

発行権の一意キーは既存の(provider, order_code, line_item_key, unit_index)を維持する。再取込で既存発行権のSKU・商品・消込状態を書き換えず、同じ明細は追加しない。

保存済み発行権がある注文の再通知については、明細キー・SKU・商品・数量が一致することを確認する。数量増加や形式変更で異なる明細へ変わった場合は`purchase_details_conflict`として保留し、勝手に発行枠を増やさない。既存のmarketplace_orders行のロック下で照合する。注文の既知代表商品も再通知で上書きしない。

未分類・ダウンロード等の再通知では既存注文行と発行権を変更しない。保留情報だけを別表へ記録する。**古い権限の自動取消・原本再計算・保存済み発行物の上書きはしない。** 誤った権限がすでに存在する場合の修復は、この作業に含まれない。

## 運営通知

新しい`marketplace_order_holds`表に販売サイト、注文ID、固定の保留理由、状態、確認時刻、メール通知状態・試行回数を保存する。本文・件名・購入者メール・出生情報は保存しない。

- 管理画面の「発行を保留した注文」で、管理トークンを用いて一覧を取得する。ページ送りに対応。
- `GET /internal/orders/holds`は既存の管理認証で保護する。購入者情報を返さない。
- 初回保留時、注文保存のコミット後に構造化WARNINGを出す。ログは販売サイト・注文ID・理由コードのみ。
- 同期結果に`held`、`new_holds`、`notification_delivery`を追加する。okは同期の完了を意味し、保留ゼロを意味しない。
- メール通知はSMTP設定が揃った場合だけ実行する。失敗時はpendingを保持し、5分以上あけて次回同期で再試行する。1回の同期で最大3件。
- 送信対象の取得にFOR UPDATE SKIP LOCKEDを使う。通常の再同期で送信済み通知を再送しない。解決後の再保留や理由変更は再通知の対象になる。

メール本文には販売サイト・注文ID・保留理由と管理画面で確認する案内のみを含める。原文や購入者への案内文を転送しない。今回のSMTPテストは全てモックであり、**実メールは送っていない**。

SMTP送信成功後、送信済み状態のDBコミットが失敗すると通知メールが再送される可能性がある。SMTPとDBの間で厳密な1回だけの配信は保証しない。これは通知の再送の制約であり、商品の発行権を増やす処理ではない。

### 配信に必要な設定

| 環境変数 | 用途 |
|---|---|
| ORDER_HOLD_NOTIFY_TO | 運営通知先（1アドレス） |
| ORDER_HOLD_NOTIFY_FROM | 通知送信元 |
| ORDER_HOLD_SMTP_HOST | SMTPサーバー |
| ORDER_HOLD_SMTP_USERNAME | SMTP認証ユーザー |
| ORDER_HOLD_SMTP_PASSWORD | SMTP認証情報（秘密管理を使用） |
| ORDER_HOLD_SMTP_SECURITY | ssl（既定）またはstarttls。平文SMTPは不可 |
| ORDER_HOLD_SMTP_PORT | sslは465、starttlsは587が既定 |

設定不足ではpendingを保持し、同期結果はunconfiguredを返す。既存のGmail読取用OAuth認証を送信用に流用しない。通知先はユーザーへ確認中で、送信元・配信認証も未設定。配信設定・実配信検証は未完了。
