## 外部SMTP確認の準備

送信対象は以前指定された運営者のテストアドレスのみ。購入者への送信は行わない。Gmailコネクターでの以前の到達確認は、アプリのSMTP経路の証明として扱わない。

アプリが読む設定項目は次のとおり。秘密値は環境変数やGit管理外の秘密設定で指定する。ファイルに置く場合は、実行環境が明示的に読み込めることも確認する。

| 項目 | 用途 |
| --- | --- |
| ORDER_HOLD_NOTIFY_TO | 運営者のテスト宛先 |
| ORDER_HOLD_NOTIFY_FROM | 使用するSMTPサービスで許可された差出人 |
| ORDER_HOLD_SMTP_HOST | 利用するSMTPサービスのホスト |
| ORDER_HOLD_SMTP_USERNAME / PASSWORD | SMTP認証。値をチャット・Git・ログへ出さない |
| ORDER_HOLD_SMTP_SECURITY | `ssl` または `starttls`。実装の既定値は `ssl` |
| ORDER_HOLD_SMTP_PORT | サービスの指定に合わせる。実装の既定値はssl=465、starttls=587 |

設定後の検証手順：

1. 本番とは別のDBに、架空の保留注文を1件だけ作る。本文・購入者情報は保存する通知に含めない。
2. 宛先が運営者のテストアドレスだけであることを送信直前に確認し、アプリの `dispatch_pending_notices` から送る。
3. 販売サイト・架空注文ID・保留理由が届き、購入者情報や注文本文が含まれないことを確認する。SMTP受理と受信箱到達を別々に記録する。
4. 隔離テストで送信失敗を起こし、pending・試行回数・最終試行時刻がDBに残ることを確認する。5分以上経過後の同期呼出しで再送を確認する。
5. 通知再送によって承認候補や発行権を変更しないこと、送信後の再実行で通常は再送されないことを確認する。

SMTP受理後のDBコミット失敗では通知が重複し得る。再送は独立タイマーではなく同期処理から呼ばれる。通知の重複と商品の二重発行は区別する。

**現在は設定がないため実配信に進めない。** 本番の秘密設定やSMTPサービスを今回新設してはいない。

## 本番導入の順序と停止条件

以下は未実行の手順案。新しい公開許可ではない。

1. **公開する変更を確定する。** 716a2aaの親には、占術修正・商品台帳・承認・SMTP・監査資料の先行3コミットがある。今回の2件だけをデプロイする状態とは異なる。先行変更の公開範囲と互換性も確認する。
2. **停止・復旧の担当者と方法を確定する。** 対象は定期同期、`POST /internal/mail-sync`、フォーム起点同期、`POST /redeem` と商品別redeem、`POST /addon/generate`、`POST /admin/addon/generate`、管理者承認、関連管理者の書込経路。候補・旧revisionの直URLも対象にする。現在確認できた設定に、全書込を止める共通スイッチはない。`STORES_MAIL_SYNC_ON_SUBMIT=0`だけでは停止できない。利用するネットワーク・認証側の停止方法と、処理中リクエストの終了確認を演習するまで導入しない。
3. **既存DBスキーマを確認する。** 必要な注文・発行権・保留・候補・確認版・処理済み通知のテーブルと列を読み取りで確認し、不足DDLを確定する。今回の限定修正自体はDDLを追加していないが、先行コミットは追加表・列を要求する。本番DDLは別の明示承認後にのみ行う。
4. **全初期化を移行代わりに呼ばない。** startupはDB初期化をスキップする。`/internal/init-db` は表を作るだけでなく、既存chartsのshare_yaml_textやexpires_atを更新し、旧注文をmarketplace_ordersへコピーする。この範囲を確認せず実行しない。同期時の `_require_stores_orders_table` はDDLを適用しない。
5. **Payhip互換性を最終確認する。** 保存した実通知の匿名フィクスチャ8件を維持し、STORES6件も確認する。正常な購入、ダウンロード通知、数量変更、旧形式の未発行注文、原本再取得を区別する。過去の誤保留を自動解除しない。根拠のない候補は無理に承認しない。販売サイトから本番発行までの実購入演習は未実施として残す。
6. **Gitと実行環境を整える。** 未追跡資料を安全に保護してクリーンにし、承認されたブランチをpushする。現在の作業ブランチにupstreamはなく、このworktreeの `.venv/Scripts/python.exe` もない。既存deployスクリプトの停止条件を回避せず、承認済みのクリーンな実行場所とPythonを用意する。一時物はOneDrive外に置く。
7. **候補を作成する。** そのターンの明示依頼後にのみ既存 `scripts/deploy_candidate.ps1` で0%候補を作る。0%でもタグURLは到達可能で、DBは隔離されない。候補では `/health` 等の読み取りだけを確認し、本番DBに試験注文やテスト保留を作らない。書込の機能確認は別の隔離環境で行う。
8. **切替を別に承認する。** スモーク確認後、そのターンの明示依頼で `scripts/promote_candidate.ps1` を使う。変更前のtraffic、revision、設定項目、運用担当者を退避してから切替する。

## 障害時の切り戻し手順

1. 誤発行、保留の迂回、原本の不一致、消込競合、同期不整合が見つかったら公開を停止する。通知だけの失敗なら発行権と切り分け、原因を確認する。
2. 確定・演習済みの方法で書込と同期を止める。処理中リクエストや残る旧・候補URLの経路も確認する。保存済み原本の読み取りを維持できるかを事前に決める。
3. 影響した注文ID・発行済み枠・未使用枠・保留・承認版・原本を、権限を持つ運営者が保存して照合する。顧客情報を一般ログや通知本文へ丸ごと出さない。
4. 切替直前に退避した実際の配信revisionと割合へ、明示承認後に戻す。`promote_candidate.ps1` は現在コミットの候補昇格用であり、任意の旧revisionへの切り戻し用ではない。切り戻し操作の具体的方法・権限は事前に別途確認する。
5. DBの追加表・履歴・発行権・原本を保持する。Gitの履歴を書き換えず、DBを過去のバックアップで丸ごと上書きしない。切替後に成立した購入や発行を失わせない。
6. 旧版が保留表を参照しない場合は発行を再開しない。通常商品だけでなく追加商品・再通知でも承認前停止を確認し、修正版か保護された運用に戻ってから書込を再開する。

**切り戻し演習、全書込の停止方法、Schedulerの停止対象は未確定。** この文書を作ったことだけで、停止・復旧できる状態になったとは報告しない。外部SMTPが届いても、これらと既存フロー・移行の確認を終えるまでは本番公開保留を維持する。
